# ADR 0012: how the members API gets its Python dependencies

- **Status:** proposed
- **Date:** 2026-08-28
- **Deciders:** TBD. `docs/plan/people-and-custody.md` section 1 has no names in it yet, and this record is not complete until a build lead signs it.

## Context

Until now this repository installed nothing. `services/door` is standard library
only and says so in its README, the database suite runs psql inside a container,
and every tool arrives as a pinned image. The members API is the first thing
here with a dependency tree, so two questions arrive together: which packages,
and how they are pinned and installed.

`docs/plan/architecture.md` section 2 already chose FastAPI, so the framework is
not in question. What is in question is everything under it.

The constraint that shapes both answers is in `README.md` and holds for every
other suite: a person runs the tests with Docker and python3 and installs
nothing on their own machine.

## Options considered

Every version, date, licence and issue count below was read on 2026-08-28, from
`https://pypi.org/pypi/<name>/json`, from the GitHub or Codeberg API for the
project's repository, or out of the installed package's own metadata inside the
built image. None of it is from memory.

### The packaging question

#### Option A: pip, with a lock generated by uv

- **Last release:** pip 26.2.1, 2026-08-04. uv 0.12.7, 2026-08-27.
- **Licence:** pip MIT. uv is `MIT OR Apache-2.0` on PyPI and its GitHub
  repository record says Apache-2.0.
- **Maintainers:** pip is the Python Packaging Authority, 395 contributors.
  uv is Astral, 468 contributors.
- **Fit:** `uv pip compile --universal --generate-hashes` writes one
  `requirements.txt` carrying every wheel hash for every platform, and the
  Dockerfile installs it with `pip install --require-hashes`, which is already
  in the base image. uv runs when somebody changes a dependency, not on every
  build, so the build needs nothing beyond the Python image.
- **Cost:** two tools rather than one, and a person regenerating the lock needs
  the uv container.

#### Option B: uv all the way through

- **Fit:** `uv sync --frozen` in the Dockerfile off a `uv.lock`, faster than pip
  and one tool for both halves.
- **Cost:** uv has to be in the image, and `uv.lock` is a format only uv reads.
  A volunteer at 2am with a broken build can read a `requirements.txt` and run
  pip by hand. That is the whole argument.

#### Option C: Poetry

- **Last release:** 2.4.1, 2026-05-09.
- **Licence:** MIT.
- **Maintainers:** the Poetry project, 440 contributors, 566 open issues.
- **Fit:** a cross platform `poetry.lock` with hashes, and the most widely known
  of the three.
- **Cost:** it wants a `pyproject.toml` describing this service as a
  distributable package, which it is not, and it has to be installed into the
  build. It buys nothing over Option A here.

#### What was measured rather than read

`pip freeze` and `pip install --report` record the wheels for the machine that
ran them. This laptop is arm64 and CI runs amd64, so a hash list generated with
pip on one refuses to install on the other. That is what sent the lock to uv,
and `--universal` is the flag that fixes it.

### The driver question

#### Option A: psycopg 3

- **Last release:** 3.3.4, 2026-05-01. Repository last pushed 2026-08-28.
- **Licence:** **LGPL-3.0-only**, read from the installed package's metadata.
- **Maintainers:** the psycopg project, 98 contributors, 75 open issues.
- **Fit:** synchronous, which is what `architecture.md` section 2 asks for. Its
  `psycopg_pool` is a pool this service can hold to exactly one connection,
  which is what makes the identity leak test in
  `services/api/tests/check_identity_isolation.py` able to see anything. The
  binary wheel carries libpq, so the image installs no build tools.
- **Cost:** copyleft, addressed below.

#### Option B: asyncpg

- **Last release:** 0.31.0, 2025-11-24. Repository last pushed 2026-02-27.
- **Licence:** Apache-2.0.
- **Maintainers:** MagicStack, 89 contributors, 300 open issues.
- **Fit:** no copyleft question at all.
- **Cost:** async only. Every route and every query in this service would become
  a coroutine to buy concurrency a few hundred members do not need, and
  `architecture.md` section 2 says synchronous.

#### Option C: pg8000

- **Last release:** 1.31.5, 2025-09-14, which is also when its repository was
  last updated.
- **Licence:** BSD 3-Clause, stated in its PyPI metadata.
- **Maintainers:** one person, Tony Locke, on Codeberg, 11 open issues. The
  Codeberg API serves no contributor list for it, so the count could not be read
  the way the other two were.
- **Fit:** pure Python, no libpq, permissive licence.
- **Cost:** one maintainer on a component in the path of every request, and it
  ships no pool.

## Decision

For packaging, **Option A**: `requirements.in` names the four direct
dependencies, uv compiles it to a universal hashed `requirements.txt`, and the
Dockerfile installs that with pip and `--require-hashes`.

For the driver, **Option A**: psycopg 3 with `psycopg[binary,pool]`.

Leading with what eliminated the others. On packaging, the platform bound hash
list is the fact: pip alone cannot write a lock that installs on both a laptop
and the runner, and uv in the build buys speed at the price of a file a person
cannot install by hand. On the driver, synchronous is a stated architectural
choice and asyncpg is not, and pg8000 has one maintainer.

### The copyleft check, per rule 9

psycopg 3 is LGPL-3.0-only. It is installed as a separate wheel, imported at
runtime, and never modified. Nothing here is derived from its source, and the
lab runs the image rather than distributing it. Under those facts the licence
reaches nothing in this repository, on the same reasoning `ATTRIBUTIONS.md`
already records for Zitadel's AGPL.

Two things change that, and both are worth knowing before they happen. Vendoring
psycopg into this tree, or building an image nobody can replace the library in
and handing it to somebody else, brings the obligation with them. If the lab
ever wants to publish the image, price pg8000 again first.

## The condition that would flip this

If a person has to change a dependency version and cannot, because the uv
container is unavailable or the universal resolve fails on a package that ships
no wheel for one of the two architectures, then the lock is costing more than it
buys and pinned versions without hashes become the right trade.

## Consequences

- The build needs network access to PyPI. Nothing else here does, and an offline
  build now needs a wheel cache that does not exist.
- Twenty one packages arrive with the four that were asked for.
  `ATTRIBUTIONS.md` lists every one with the licence read from the package.
- Changing a dependency is two steps: edit `requirements.in`, regenerate
  `requirements.txt`. The header of the generated file is the command.
- Reversing this is cheap. `requirements.txt` is a plain pip file, so dropping
  uv means dropping the hashes and hand pinning, which is one edit and a
  paragraph in this file.

## What this ADR does not decide

`architecture.md` section 2 names SQLAlchemy 2.0 and Alembic beside FastAPI, and
this service uses neither. It runs three read queries as SQL text, and the
schema is applied by `db/migrations` through psql, which is the mechanism
`db/tests/run.sh` exercises on every run and the one the legacy import,
the backup drill and the bootstrap suite all build on. Adding Alembic would put
a second migration system beside that one.

Neither of those is settled here, because neither is a packaging question and
both deserve their own record. What is settled is that this slice does not
introduce them, and that a later change adopting either should supersede
`architecture.md` section 2 rather than quietly doing it differently.

## Open questions

- The lock is generated by hand today. Nothing checks that `requirements.txt`
  still matches `requirements.in`, so a direct dependency added to one and not
  the other goes unnoticed. Resolved by a CI step that recompiles and diffs.
- `ATTRIBUTIONS.md` says its dependency table is generated by
  `tools/attributions/generate.py`, which does not exist. This change adds the
  first lockfile in the repository and lists its contents by hand. Resolved by
  writing that generator against this file.
