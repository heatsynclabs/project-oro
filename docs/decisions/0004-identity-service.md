# ADR 0004: the identity service

- **Status:** accepted
- **Date:** 2026-08-28
- **Deciders:** TBD. `docs/plan/people-and-custody.md` section 1 has no names in it yet, and this record is not complete until a build lead signs it.

## Context

The lab's Rails 3.2.8 application holds every member's password as a bcrypt hash
written by Devise: the modular crypt string `$2a$10$...`, cost 10, no pepper.
Nobody has the plaintext and nobody ever will. Whatever replaces that
application has to accept those strings as they are and let a member sign in
with the password they already use, or every member is locked out on cutover
day and the migration turns into a password reset for the whole membership.

Two further constraints, both from `docs/plan/architecture.md`: the login screens
must be the provider's own, branded, rather than written here, because a bespoke
login page is a credential path this lab would maintain forever; and the whole
thing must run from a compose file on hardware the lab owns.

`docs/plan/order-of-operations.md` line 177 has referred to "the identity ADR"
since the plan was written. This is that record, arriving late.

## Options considered

Versions, dates, licences and source quotations below were read on 2026-08-28
from each project's own repository or documentation.

### Option A: Zitadel

- **Last release:** 4.17.1, 2026-08-14. 1,138 open issues.
- **Licence:** AGPL-3.0. Run as a published container, unmodified, as a separate
  process reached over HTTP, so its copyleft reaches nothing here.
  `ATTRIBUTIONS.md` carries that check.
- **Maintainers:** a company, with five contributors over 250 commits each.
- **Fit:** proven, not documented. `cmd/defaults.yaml` at the release tag sets
  `PasswordHasher.Limits.Bcrypt.MinCost: 10`, so a cost 10 hash is exactly at
  the accepted floor with no configuration. Measured end to end this session
  against a running instance: hashes generated by bcrypt-ruby 3.1.20 at cost 10
  imported through `POST /v2/users/human` with `hashedPassword.hash`, and each
  member signed in through `POST /v2/sessions`. Its own hosted login screens,
  brandable. The first instance, the admin, and a machine account with a token
  written to a file are all created from environment variables, so a deployment
  needs no console click.
- **Cost:** a password longer than 72 bytes cannot sign in, and the refusal
  arrives as HTTP 500 rather than as a wrong password. Measured, with the
  boundary at exactly 72 bytes. `tools/identity/README.md` has the detail and
  the suite asserts it.

### Option B: Logto

- **Last release:** 1.42.0, 2026-07-30. 178 open issues.
- **Licence:** MPL-2.0, which is friendlier than the AGPL.
- **Maintainers:** five contributors over 1,200 commits each.
- **Fit:** it also does this, and that matters because two documents in this
  repository said Zitadel was the only candidate that could. It is not.
  `packages/schemas/tables/users.sql` declares
  `users_password_encryption_method` with `'Bcrypt'` in it,
  `user-password-verification.ts` dispatches that case to `bcryptVerify`, and
  its own unit test verifies a `$2a$12$` string. Import is `passwordDigest` plus
  `passwordAlgorithm` on `POST /api/users`. Hosted, brandable login screens.
- **Cost:** none found on paper. Nothing here has been run against it.

### Option C: Keycloak, the obvious default

- **Last release:** 26.7.2, 2026-08-19.
- **Licence:** Apache-2.0.
- **Maintainers:** Red Hat, many.
- **Fit:** everything except the one thing that decides it.
- **Cost:** **it ships no bcrypt verifier at all.** The two service registration
  files list four password hash providers between them: argon2, pbkdf2-sha512,
  pbkdf2-sha256 and pbkdf2. The string "bcrypt" appears three times in the whole
  repository, in a Javadoc comment and in a test that round trips an algorithm
  name through a data object. Reading a Devise hash means writing a Java
  `PasswordHashProvider`, packaging it as a JAR, dropping it into `providers/`,
  and running `kc.sh build` on every upgrade, forever. Provider JARs are not
  loaded in an isolated classloader, so that code sits inside the server on
  every login. That is a credential path the lab would own and patch, which is
  the thing this project is trying to stop doing.

### Option D: Ory Kratos

- **Last release:** 26.2.0, 2026-03-20.
- **Licence:** Apache-2.0.
- **Fit:** the hash side is excellent. `hash/hash_comparator.go` sniffs
  `^\$2[abzy]?\$` and dispatches to `CompareBcrypt`, import is `hashed_password`
  on `POST /admin/identities`, and cost 10 is inside its accepted bound.
- **Cost:** self hosted Kratos ships no login screens. Its own documentation
  says so plainly: "In stark contrast to other Identity Systems, Ory Identities
  doesn't render this HTML. Instead, you need to implement the HTML code in your
  application." That is the bespoke login page this project refuses, so it is
  eliminated on the second constraint rather than the first.

### Option E: Authentik

- Rejected. It is Django and defers to Django's hashers, whose only bcrypt
  entry pre hashes with SHA256 and is therefore a different function. Django
  identifies a hasher by the text before the first `$`, which for `$2a$10$...`
  is the empty string, so the hash is not merely unverifiable, it is
  unrecognised. Making it work means a Python hasher class mounted into a file
  the project's own documentation calls "not supported", plus rewriting every
  hash string with a prefix.

## Decision

**Zitadel.**

The claim that eliminated everything else is that Keycloak, the default anybody
would reach for, cannot read a Devise hash without a JAR the lab maintains. That
is now evidence rather than assertion, which it was not before this record.

Between the two candidates that can, Zitadel is chosen because it has been run
against this repository's own fixtures and Logto has not. That is a weak
reason to prefer one over the other and it is stated as one. The strong reason
to write it down at all is the correction underneath it: **Zitadel is not the
only candidate that imports these hashes**, and until today two documents here
said it was. Logto is a live alternative, not a fallback.

The reasons that are not doing the deciding, stated so nobody mistakes them for
the argument: Zitadel is a single Go binary in a distroless image against
Logto's Node runtime, which is a smaller thing to patch; and Zitadel's AGPL is
the worse of the two licences here, which is a point against it rather than for.

## The condition that would flip this

Any of these, and each is checkable:

- A real member's hash from the staging copy fails to verify. Phase 2 already
  says stop and switch rather than work around it.
- The 72 byte defect turns out to matter to real members, and Logto's
  `bcryptVerify` proves not to have it. That is a ten minute test and it has not
  been run.
- The volunteers who end up maintaining this are a TypeScript group.

## Consequences

- The stack now runs a fourth service and a second database on the same Postgres
  server. `db/init/001_identity_role.sql` creates the role and the database
  before it starts, so the identity service never holds the Postgres superuser
  password. Rule 13, one holder per secret.
- A new secret to hold and to back up: the master key, which encrypts every
  secret and signing key in the identity database. Losing it loses the database.
- Access tokens are ten minutes, set as configuration rather than left at the
  twelve hour default.
- **A member whose password is longer than 72 bytes cannot sign in and cannot be
  identified in advance.** `tools/identity/README.md` carries the measurement
  and what the options are. This is the single most important consequence on
  this page and it was found by running the thing rather than by reading about
  it.
- The AGPL means anyone who ever patches that image owes the modified source to
  its users from that moment.
- Reversing this costs the compose block, the init script, the environment
  variables, the suite, the Caddy route, and the database healthcheck, which now
  asks for the `identity` database and would keep the stack from ever starting
  if the init script went and it did not. The member data is untouched either
  way, which is the whole reason credentials live in a separate database.

## What was borrowed

Zitadel, AGPL-3.0, run unmodified as a published container image pinned by
digest in `compose.yaml`. Nothing is vendored and no code is copied. Recorded in
`ATTRIBUTIONS.md`.

## Open questions

- Whether Logto has the 72 byte defect. The test is: hash a known password with
  bcrypt-ruby at cost 10, `POST /api/users` with `passwordAlgorithm: "Bcrypt"`,
  and sign in. Worth an hour before phase 2 exits, because the answer could flip
  this decision.
- Whether the bootstrap token should exist at all. It administers the whole
  instance, it is written once into a volume and is durable across restarts and
  recreates, it expires in a year, and nothing revokes it. Registering the four
  OIDC clients is the moment it stops being needed, so the two belong in one
  change. The alternative is to mint no token and have a human administrator
  create a service account, which trades a standing credential for a console
  click that phase 2 says should not be needed.
