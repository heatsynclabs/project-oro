# Identity

## What it is

The proof that the identity service can hold the passwords HeatSync Labs members
already have, and the fixtures that proof runs on.

The identity service itself is not code in this repository. It is Zitadel, run
as a container, configured in `compose.yaml` and chosen in
[ADR 0004](../../docs/decisions/0004-identity-service.md). What lives here is the
part of phase 2 that a script can settle: the configuration step that registers
the four clients and the branding, and the two suites that prove it.

`docs/plan/order-of-operations.md` phase 2 splits the password proof in two,
because the obvious criterion cannot be run. Signing in as twenty real members
needs their passwords, and the whole point of a hash is that nobody has them.
So:

- **Part (a), here.** Hashes generated by `bcrypt-ruby` at cost 10 with no
  pepper, which is what the legacy application writes through Devise, imported
  into the identity service and signed in with. Fully automated.
- **Part (b), not here and not automatable.** Ten real members signing in to
  staging with the password they already use. It needs the production hashes and
  it needs volunteers. Phase 2 does not exit without it.

## How to run it

```sh
make identity-test
```

That brings up a Postgres and an identity service on their own ports as a
throwaway compose project, reads the bootstrap token out of the container, runs
`configure.py` twice, then both check files, and takes it all down. Twenty seven
checks: sixteen on the passwords, eleven on what was configured and on one whole
sign in. It is the slowest suite in this repository, because the identity service
applies its own schema and seeds an instance before it answers anything.

To run the checks against a stack you already have up instead:

```sh
ORO_IDENTITY_URL=http://localhost:8180 ORO_IDENTITY_TOKEN="$(docker compose cp identity:/bootstrap/pat - | tar -xO)" \
  python3 tools/identity/tests/check_identity.py
```

Every account it creates carries a run identifier, so doing that twice against
one stack does not fail on names the first run made. Set `ORO_IDENTITY_RUN` to
choose that identifier; it defaults to the process id.

To regenerate the fixtures, which is not part of the suite and not part of CI:

```sh
tools/identity/tests/generate_hashes.sh
```

That compiles `bcrypt` in a throwaway `ruby:3.3-alpine`, so nothing is installed
on the machine running it.

## What it found

**A password longer than 72 bytes cannot sign in, and the refusal arrives as a
server error rather than as a wrong password.**

This is measured, not predicted. `bcrypt` reads at most 72 bytes of input.
Ruby's implementation truncates silently, so the legacy application accepts a
password of any length and verifies it against its first 72 bytes. Go's refuses,
and the identity service turns that refusal into HTTP 500 with the text `An
internal error occurred`. Read from the running service's own log on 2026-08-28:

```
err.parent="bcrypt: password length exceeds 72 bytes"
err.reportLocation.filePath=.../internal/command/user_human_password.go
```

Measured boundary: 71 bytes signs in, 72 bytes signs in, 73 bytes does not.

Two things follow, and both matter more than the defect itself.

**Bytes, not characters.** A passphrase of 27 Japanese characters is 81 bytes.
Nothing about it looks long, and its owner has no way to guess why signing in
stopped working. That case is in the fixtures.

**Nobody can be warned in advance.** The affected members cannot be identified
from the hashes, because identifying them would need the plaintext. The only
thing that finds them is somebody trying to sign in, which makes part (b) the
detector rather than a formality, and makes the cohort worth choosing for a
range of password habits rather than a range of account ages alone.

What to do about it is not decided here. The options are to raise it with
Zitadel so the refusal at least reads as a credential failure, to accept it and
write the recovery into the runbook, or to force a password reset for everybody
at migration, which is the only complete fix and costs every member an email.
The suite asserts the behaviour as it stands, so whichever is chosen, a change
in it fails a check rather than passing quietly.

## What is here

| File | What it is |
|---|---|
| `configure.py` | Registers the project, the three portals as public PKCE clients, the door service machine account, and the GANTRY branding. Idempotent |
| `api.py` | Calls to the management API, shared by the configuration step and the suites |
| `flow.py` | One whole sign in, driven through the hosted screens with a cookie jar |
| `tests/check_identity.py` | Part (a) of the password proof |
| `tests/check_configuration.py` | What was configured, read back, plus the sign in and what the tokens do afterwards |
| `fixtures/legacy-hashes.json` | The hashes, committed |

`configure.py` takes an origin per portal and derives none of them from another.
The three portals do not share a hostname on a deployment, and guessing one from
another is the mistake [ADR 0002](../../docs/decisions/0002-mock-server.md)
records.

## What it depends on

| Thing | Why |
|---|---|
| `compose.yaml` and `compose.development.yaml` | The identity service and its database. The suite starts them itself |
| `tools/identity/fixtures/legacy-hashes.json` | The hashes. Committed, so the suite is deterministic and needs no network beyond the images |
| `docs/plan/order-of-operations.md` phase 2 | What is being proved, and what is deliberately not |

Nothing else. Standard library Python, and Docker.

### Why the fixtures are committed rather than generated on every run

The hashes in production were written years ago and will never change. A bcrypt
hash carries its own cost and salt, so the string is the whole of the input to
this proof, and regenerating equivalent strings on every run would add a gem
install and a compiler to the suite in exchange for nothing. The generator is
kept, and it names in its own header exactly what it ran, so the fixtures can be
reproduced rather than trusted.

Every password in them is invented. Rule 13 of `CLAUDE.md`: no fixture may
resemble a credential anybody holds.
